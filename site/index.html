One rule, then Claude handles it

You state the rule once, in plain words or as a team setting. From then on, when a prompt matches, Claude starts a small Haiku subagent that carries the job to the cheaper model and brings back only the result. You keep talking to Claude the whole time.

The cheaper model works in a sandbox, on its own git worktree. Its edits come back as a diff, and Claude reads the diff and runs the tests before anything lands in your repository. That check is in the price: on the unit-test runs, Claude’s own share was most of the bill.

When no rule covers a job, an engine prices every model that could do it, Claude included, and the work stays on Claude whenever handing it off wouldn’t save anything. Small edits and plain questions never leave.

Set the rule once for the whole team

On Team, an owner writes the rule and every seat gets it. Nobody has to remember to route their test-writing. It happens when they ask Claude for tests.

Members can still write rules of their own, but a member’s rule can only make the team’s stricter. The same holds for rules that arrive inside a cloned repository.

Each member gets a share of the monthly budget, and the tools that spend money enforce it on their machine. A spend dashboard shows the owner where it went.

It also does what Claude can’t

Claude can’t watch a video, hear a recording or make an image. It has a workaround for each: it pulls still frames, installs a local speech model, draws SVG. p0ssess sends the actual file to a model that can take it, through the same hand-off.

You set the limits

Routing work to other models only saves money if it can’t run away with it. The limits are yours, and the tools that spend are the ones that enforce them.

A budget it can’t overspend

You set a monthly cap and a per-task limit. Under the limit a job just runs. Above it, Claude asks first, in one line with the cost. A quiet segment in your status line keeps the running total in view.

A sandbox for the other model

Coding work runs in a sandbox with no access to your home directory, your SSH keys or your credentials, and no route to your local network. Your OpenRouter key stays in a proxy the model can’t reach.

What it won’t do

It won’t send prompts to providers that train on them, and it won’t spend past your cap. Critical work such as auth, infrastructure, production or money stays with Claude unless a rule of yours says otherwise. Install the free plugin

Two commands and an OpenRouter key. Releases are served from the project’s own repository, next to the source, so you can see exactly what you run.

  1. Add the plugin to Claude Code.

    claude plugin marketplace add <repository URL>
claude plugin install p0ssess@p0ssess

  2. Put your OpenRouter key where p0ssess reads it.

    mkdir -p ~/.config/p0ssess/secrets
install -m 600 /dev/null ~/.config/p0ssess/secrets/openrouter_key
"${EDITOR:-vi}" ~/.config/p0ssess/secrets/openrouter_key

  3. Start Claude Code and run /p0ssess:p0ssess-me. Then tell it your first rule. Settings changes wait for your yes, and p0ssess setup undo reverts them.

What you need

Claude Code 2.1.319 or later, on any Claude plan or an API key, and an OpenRouter API key for the other models to bill to. The local sandbox for coding work needs Linux with rootless podman. On macOS and Windows, media and one-shot jobs work without it, and Pro’s cloud sandbox covers the rest.
