This policy is about the p0ssess cloud sandbox, a Pro feature run by New Deal Systems LLC, an Idaho limited liability company ("we", "us"). It says what happens to your code when a sandbox session runs. The privacy policy covers the rest of the services.

Our five commitments

  1. Only git-tracked files are uploaded.
  2. Files that look like secrets, and repositories marked .p0ssess-private, are never sent.
  3. Everything is deleted when the session ends.
  4. No content is logged.
  5. The service runs in one US region at launch.

The sections below give the facts behind each one.

1. Only git-tracked files are uploaded

When a session starts, the plugin sends a compressed copy of the files git tracks in your repository, up to 200 MB. Untracked files, ignored files and build output stay on your machine. Submodule contents are left out too.

The upload is the files as they are in your tree (for an edit session, a worktree of your current commit). It does not include your git history. The sandbox host starts a fresh git repository from that copy.

Your laptop's folder path is never sent. The plugin sends only the repository's base name, with any odd characters replaced, as the folder name inside the sandbox.

Git-tracked means exactly that. If a secret is written inside a tracked source file, the file goes up with it, because the plugin matches file names and does not read file contents to look for secrets. Keep secrets out of tracked files.

2. Secrets and private repositories are never sent

The plugin skips files whose names look like secrets and tells you which ones it skipped. The sandbox host checks the same list again and rejects an upload that holds one. The names include:

  • .env and .env.<anything>, .envrc, .netrc, .pgpass, .git-credentials, .npmrc, .pypirc, .htpasswd
  • names starting with id_rsa, id_dsa, id_ecdsa or id_ed25519
  • names ending in .pem, .key, .p12, .pfx, .kdbx, .jks or .keystore
  • names starting with credentials
  • names with secret or secrets as a word, such as client-secret.json
  • any path with a .ssh, .gnupg, .aws, .kube or .docker folder

A repository that contains a file named .p0ssess-private is refused. The plugin does not start a cloud session for it, and the host refuses it again if one arrives.

Your OpenRouter key never leaves your laptop. The sandbox's model requests travel over one encrypted connection (TLS 1.3) that your plugin opens to the sandbox host. The plugin adds your key, checks the session's cost cap and forwards the request to OpenRouter. A compromised sandbox host holds no key and cannot spend past the cap. Your device token is not shown to the host either. The host sees a short-lived signed ticket instead.

The plugin does not forward other OpenRouter calls, such as key or credit lookups, for the host.

3. Everything is deleted when the session ends

A session ends when you finish it, when 30 minutes pass, when the connection from your plugin has been gone for 90 seconds, when the upload does not finish within 5 minutes, or when the sandbox fails. In every case the containers stop and we delete the workspace, the sockets and the session record.

Nothing is cached between sessions. Each session starts from a clean environment.

The edits the agent makes come back to your machine as a diff. After the session, we do not keep the diff.

For ten minutes after a session ends, the host answers requests about it with the end reason only, and then forgets the session id.

We do not back up sandbox workspaces.

4. No content is logged

The sandbox host does not log file names, paths, commands, prompts, model requests or answers, or diffs. It does not store the model requests that pass through it. It keeps only these log entries for each request:

  • the session id
  • a SHA-256 prefix of your account id
  • the request method and route template
  • the status and byte counts
  • durations
  • the reason the session ended

These logs help us run the service and find abuse. They are kept for 30 days.

OVHcloud US runs the machines and may keep its own infrastructure logs under its own terms.

5. One US region at launch

The sandbox runs in one region in the United States, at OVHcloud US. We do not move a session to another region. If we add regions later, we update this policy and tell Pro customers before it applies.

How the sandbox is set up

Each session runs in two sealed containers under gVisor, an isolation layer that sits between the code and the host. The environment has no network of its own. The commands you run can reach package registries (npm, PyPI, crates.io, the Go module proxy and Maven Central) through a filtering proxy, and nothing else, unless you turn on full internet access for the project. With full internet access, the sandbox can reach public internet addresses on ports 80 and 443, and the sites you reach can see traffic coming from our network. Names that resolve to private addresses are refused.

Registries you download from will see the package requests that your session makes.

Each session gets 4 GiB of memory, 2 CPUs and a 30-minute limit, and you can run one session at a time. Your plan has a monthly allowance of sandbox hours, set with the prices. To apply it, the host adds up the wall time of your sessions each month, against your account.

The sandbox host never calls our account store. It gets a ticket that shows you are a Pro or Team customer, and nothing more. A ticket is checked when a session begins. If Pro ends mid-session, that session can finish.

What you should do

  • keep secrets out of tracked files
  • put a .p0ssess-private file in any repository that must never go to the cloud
  • read the diff before you keep a sandbox's changes

Changes

If we change this policy, we post the new version with a new effective date. For a change that reduces any of the five commitments, we tell Pro customers by email before it takes effect.
